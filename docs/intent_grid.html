What this grid cannot see

Read this BEFORE the numbers above. Every meter on this page measures only what the harness can assert; these are the things we know are wrong and cannot yet mechanically check. Listing them here is the point — a grid silent about its blind spots reads as complete.

blind spotwhy it isn't fixed herewhat closes it
the corpus cannot yet tell an EARNED refusal from a LAZY one
32 rows expect `chosen: null` (REFUSE AND ASK) and the harness asserts exactly that — which a refusal that never investigated satisfies perfectly. The user's ruling of 2026-07-16 (memory: feedback-earn-the-refusal) says a refusal is legitimate ONLY after investigating, and must NAME which reason: (a) the user gave too little, or (b) our own investigation came up empty / what it found fails our conditions. This corpus was mined BEFORE that ruling, so no row encodes it.		The obvious patch — assert the refusal carries candidates — is WRONG for the vendor-gated rows: `dragen` is in no registry and has no installable repo, so an empty candidate list IS the honest reason (b). The correct assertion needs a `refusal_reason` field on the decision, which does not exist yet. Inventing a field to assert against would make the corpus agree with itself while drifting from the code — the disease this whole audit is about.Add `decision.refusal_reason` ∈ {needs_user_input, investigation_empty, investigation_contradicted} + the evidence that backs it, extend `probe()` to read it, add `expect.refusal_reason` to these 32 rows, and promote them. THEN this gap closes. Live proof it is real: `resolve('dorado')` never runs github discovery at all (probe_github_search fires ONLY at a registry dead-end, and PyPI's astronomy package counts as a hit) — so nanoporetech/dorado, 849 stars, exact name match, is never even looked for. That refusal would not be earned.
the identity half of the `report` gap is DISSOLVED, and its replacement is not yet measured
THE AUTHORS'-PATH HALF STAYS CLOSED (2026-07-17): expect.authors_gate asserts which of four things happened to the reliability gate (assessed / not_assessed / errored / no_repo), and 4 rows carry it — that caught trinity-author-image-tier-probes-the-ethereum-repo, which was recorded is_correct_today=TRUE and PASSING the whole time the author tiers probed ethereum/trinity, because it only asserted chosen=='conda' (true) while the thing it guards was broken: green with the wrong tool in it, inside the corpus built to expose exactly that. THIS GAP NOW CONCERNS THE IDENTITY HALF. Until Phase 2 (2026-07-17) the report gap's identity half was: the resolver stamped a confident identity VERDICT (identity.confirmed/anchor/evidence/note) that could be FALSE on right-tool/right-bytes picks — perl-json 'confirmed' on 'bioconda is a bioinformatics-only channel', a proposition its own self_description ('JSON encoder/decoder') disproves on the same screen. Phase 2 DELETED the verdict outright (the reverse-theme-park ruling: the LLM ride is the identity judge, not an 86-word list). The resolver now emits identity FACTS only — self_description, has_description, channel, repo, repo_source, repo_anchored — and never a verdict. There is no longer a fabricated confirmation to be false, so the ~7 rows that were assertable:false 'waiting for Tier 8 to expose anchor/evidence/note' are waiting on fields that no longer exist.		Three things replace the old measurement and each needs work this offline pass cannot do. (a) The mechanically-checkable successor — does the resolver SURFACE the facts the LLM needs (has_description True, self_description = the tool's own words, repo_anchored correct) — needs a live re-probe to populate actual_today with the new facts (and a GITHUB_TOKEN, or the author-tier rows rate-limit and corrupt authors_gate). (b) Residual non-verdict defects survive on some rows (deprecated-tools wants a FITNESS finding surfaced; false-accusation/rename/org-move want the false cross-namespace collision suppressed) — those are separate from the deleted verdict and keep their own gap. (c) The deepest one: whether the LLM's identity JUDGMENT actually lands ('is this the tool you MEANT?') is now the ride's job, and resolve()-probing structurally cannot see it.Re-probe each report row's new facts and re-grade: promote the rows whose ONLY defect was the deleted verdict, add a facts-surfacing assertion (has_description True + self_description content + repo_anchored) where checkable, and keep a scoped gap for the residual fitness/collision defects. Then build an LLM-in-the-loop eval for the judgment itself — feed the surfaced facts to the ride and score whether it reaches the tool the user meant. That eval, not a resolve()-probe, is the honest successor to the old verdict assertion.
3 rows are PARKED as unassertable: they contradicted a sibling on an identical call
Found 2026-07-17 by the new mechanical check (test_rows_sharing_a_call_do_not_demand_contradictory_outcomes). {tool: seurat}, {tool: limma} and {tool: bcftools, github_repo: populationgenomics/bcftools} each had TWO rows demanding mutually exclusive `chosen`. Every one was the same slip: the verify pass rewrote one row's expect — saying so in the note ('EXPECT REWRITTEN ... is REFUTED') — and never propagated to its sibling. Both were xfail, so they were quiet; under strict xfail the day either got fixed the other became a PERMANENT red no fix could clear, which is how a corpus earns being ignored. The measured surface therefore SHRANK from 50 assertable rows to 47. That is the honest number: those 3 were never measuring what they claimed.		Each parked row's UNIQUE content is real but not yet expressible: seurat's is that an empty-description PyPI stub must not read as a real candidate (needs identity.evidence); limma's is STALENESS ('right project, wrong decade' — no field exposes it); bcftools's needs api.github.com stubbed to 403 and its `call` is a byte-duplicate of fork-is-the-point, so an R.resolve(call) runner silently executes the WRONG scenario.seurat -> expose identity.evidence (see known_gaps[1]). limma -> a staleness field. bcftools -> nothing: its demand is ALREADY MET one level down, where it belongs, by tests/test_probe_honesty.py::test_github_repo_probe_does_not_report_a_rate_limit_as_a_missing_repo. Delete it rather than restore it.
