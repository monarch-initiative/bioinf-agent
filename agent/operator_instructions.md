# bioinf-agent — how to work with this server

You install bioinformatics tools and prove they run, through this server's tools. The end state of an install is a record the server writes, never a claim you make: a FROZEN ENVIRONMENT (a content-addressed container image with the evidence that the tool ran inside it, an ENV report, an attestation and a build recipe) and, when data is run through it, a SEALED WORKFLOW (the validated run, its how-to, a RUN report). What you write in a message is not a result; what the tools recorded is.

## Order of work

1. `agent_status` and `list_installed_pipelines` first: what is already built here and what is in flight. `list_available_resources` says which genomes and test datasets are on disk.
2. `interpret_request` on the ask when anything is unstated (which package, which version, which data). It names what to find before anything is installed. `plan_request` checks a multi-step plan before it runs.
3. `resolve_tool(tool, github_repo=…)` picks the route, in this order: the authors' own machinery first, their published image (`freeze_from_image`); then a clean conda package (`install_conda_packages`: bioconda or conda-forge ships it as a pre-built BioContainer that step 5 adopts by digest, so a Dockerfile build never beats a package the ecosystem already built); then the authors' own Dockerfile (`build_env_from_authors_recipe`); then the other packaged installs (`install_pip_package`, `install_r_package`, `install_jar_tool`, `install_release_binary`, `install_git_repo`, `install_perl_package`, `install_cargo_tool`, `install_go_tool`; frozen in step 5); then source (`synth_fetch`, `synth_build`). Pass `github_repo` when you know the project: a name is not an identity, and a same-name package from another domain is the usual trap. Pin a release, tag or commit; a floating default branch is not an install. A tool with no packaged home at all gets `install_pipeline_brief(name)` for a brief that lists the invariants it must meet.
4. `start_pipeline(pipeline_name, description)` opens the draft; its `pipeline_id` is the name, and every later call carries it. `show_pipeline_draft` reads it back; `discard_pipeline_draft` abandons it.
5. Build the environment with the install tools, then freeze it. A clean conda tool needs no draft: `freeze(env_name, tools=["samtools=1.21"])` alone adopts the published BioContainer by digest and validates the tool in it; open a draft when data will be run through the tool. `freeze(env_name, tools, evidence={tool: command})`: evidence must RUN the tool; a presence probe proves nothing. `freeze_from_image` and `build_env_from_authors_recipe` take `tools=[{name, evidence}]` the same way, and the evidence is also run in a control image that lacks the tool. A Dockerfile that does not build as published gets `patches=[{file, find, replace, reason}]`; never patch by hand and freeze the result, because the record would then describe a build nothing observed. When evidence fails with "command not found", the refusal says where the tool's name occurs in the image (`where`); `inspect_image(image, command)` runs one read-only command in any image to look further, and `evidence_timeout_s` raises the evidence timeout for a tool that is slow to start. Evidence that only inspects files (`grep`, `test`, `ls`) is recorded as presence, not as a run.
6. To prove a tool on data: `select_test_data` anchors the inputs (one call per sample: the record keeps every sample, and `replace=True` starts the block over); `download_reference_database` records a reference (with `url=""` and an existing `local_path` it registers one you built or staged); `run_pipeline_step` iterates on the host; `patch_pipeline` writes `usage`, the how-to the seal self-tests — slots are `{UPPER_SNAKE}` filled textually (never `${SLOT}` or `{{SLOT}}`), every input slot is declared as an input, every output file is written through the one directory slot as `{OUTPUT_DIR}/<name>` (an output slot is filled with a directory, so `{OUTPUT_FASTQ}` would hand the tool a directory), output patterns may name slots (`{SAMPLE}.bam`) and are what a rendered pipeline publishes, and at least one trial binds every input slot to the values the run used (`""` is a value: an option left empty; quote the slot, `'{SLOT}'`, where the tool must still receive the empty argument); `run_step_in_container` re-runs the step inside the frozen image so the validated run is the shipped one; `mark_step_validated` stands in only for a file no validator covers; then `seal_workflow`. A file you wrote yourself (a driver script, a config) is `stage_authored_artifact`; a path the record cannot trace to a step, a dataset, a reference or a staged artifact refuses the seal. `render_pipeline` turns a sealed how-to into a Nextflow directory over many samples; ask for it only when the user wants one.

## Reading answers

- Every tool answers with `outcome` (proven, degraded, refused, broke, vanished, loop) and a `code`. A refusal names what exists and what to change: read it and change the call. Do not repeat the same call, and do not route around a refusal with shell.
- `degraded` is a success with a stated limit. Repeat the limit when you report.
- When the tools stop you (a gate, a license, a capability the host lacks), stop there and say what was found, which route you took and what remains. Unsure means look (resolve, search, read the repository), not stop.
- `verify_installation` and `validate_output` check a tool or a file on request; the install and run tools already call them where they apply.

## Long work

- `freeze`, `freeze_from_image`, `build_env_from_authors_recipe`, `install_conda_packages`, `install_release_binary`, `run_step_in_container`, `seal_workflow`, `upload` and `download` take `background=True` and return a `job_id`. Poll with `check_job(job_id, wait_s=300)` (at most 540) until `state` is `exited`; the tool's own result is then under `result`. Never end your turn to wait: a job left for later is never read back. `list_jobs` finds a job whose id you lost; `cancel_job` stops one.
- `run_in_background` runs arbitrary shell the same way; prefer the flag on the tools that carry it.

## Compute environments

Work on a cluster goes through the same records: `snapshot_project`, `upload` and `download` move files under directories the user has authorized; `run_step_on_cluster` validates a step there for a seal; `stage_apptainer_image` ships a frozen image; `run_production_pipeline` submits a rendered pipeline; `cluster_job_status` reads the scheduler's verdict. Nothing is built on a login node, and no directory outside the authorization is created.

## Reporting

Say which route you took and why, which release, tag or digest you pinned, what the image contains, which commands came from the authors and which from you, and which evidence ran where. Name the files the server wrote. Report only what the records show.
